# Loco 製品評価 — ソクラテス式点検

**更新: 2026-09-01。** 以前の版(2026-07 作成・08 追記)は解決済みの問題を
「未解決」として掲げ続けていた。数値も主張も古かった。

この版の書き方は前版と違う。項目ごとに **問い → 証拠 → 評決** を書く。
証拠は `file:line` か実行結果に限り、「実装した」「対応済み」といった伝聞は
証拠として採らない。この方針自体が、このリポジトリで最も多くの欠陥を
見つけた手法だったからである — 「その機能は本当に存在するか?」と問い、
grep とコンパイラとテストに答えさせる。

## 検証の土台

**問**: このリポジトリについて、何を根拠に「動く」と言えるのか。

**証拠**: `./scripts/verify.sh` が一括で走る。ネットワーク不要。

| 検査 | 内容 | 現在 |
|---|---|---|
| `scripts/typecheck-offline.sh` | `src/` と `tests/` の全 C# を Roslyn でメソッド本体まで型検査 | **0 エラー** |
| `scripts/check-structure.py` | 7 つの構造検査(下記) | **7/7** |
| `scripts/run-tests-offline.sh` | バックエンドテスト全件 | **335 passed / 0 failed** |
| `npx vitest run` | エディタ | **444 passed / 38 files** |
| `npx tsc --noEmit` / `npm run build` / `npm run lint` | エディタ | クリーン / 警告 55(0 エラー) |

構造検査の 6 つは、いずれも**実際に欠陥を捕まえた**ために存在する:
パッケージ管理の整合性(NU1008 で restore が 1 パッケージも取得せず失敗していた)、
テストが参照する型の実在(存在しないクラスを名指す 2 ファイルがテスト
アセンブリ全体を落としていた)、`src/` 全ファイルの到達可能性(4.4 万行が
どこからも到達不能だった)、SDK が叩く API 経路の実在(両 SDK が存在しない
ルートを叩いていた)、エディタ各モジュールの到達可能性(3,268 行が import
不能だった)、エディタのページが参照する静的ファイルの実在(`index.html` が Vite
テンプレート既定の `/vite.svg` を参照したまま `public/` が存在せず、
全ページロードで 404 だった)、ドキュメントが参照するファイルの実在(33 文書が
存在しないシステムを解説していた)。

**評決**: 主張は再現可能。ただし後述の「実パッケージビルド」だけは別。

## 長所

### 問: バックエンドのテストは本当に走るのか

**証拠**: `scripts/run-tests-offline.sh` が 335 件を実行する。うち 33 件は
コントローラテストで、`scripts/offline-test-harness/WebApplicationFactory.cs`
が **API を実 exe としてループバックポートで起動**し、本物の Kestrel に
本物の HTTP で話す。「秘密がレスポンスに現れない」という表明は、実際に
ソケットを通過したバイト列に対する検証である。

緑が嘘でないことは変異試験で確認した:
接続作成時のレスポンスに秘密を混ぜると `ConnectionsApiTests` が 4 件落ち、
署名鍵を検証鍵と別物にすると 3 クラス 12 件が落ちる。

**評決**: 走る。`dotnet test` ではないが、アサーションは本当に評価されている。

### 問: 28 個のコネクタは実行時に成立するのか

**証拠**: `JsonFileConnectionStore`(AES-256-GCM / PBKDF2 600k)→
`ConnectionsController` + `ConnectorsController`(コネクタが宣言する資格情報
フィールドを公開)→ `ConnectionsManager`(その宣言をフォームとして描画)→
`WorkflowCredentialResolver.ConfigureAsync`(API と CLI が共有)。
`WorkflowConnectorBridge` は `(connectorId, credentialId)` ごとにインスタンスを
持つので、1 ワークフローで Slack の 2 ワークスペースを同時に使える(`be24736`)。

**評決**: 成立する。以前は `ConfigureConnector()` の呼び出し元がゼロで、
全コネクタが null HttpClient で失敗していた。

### 問: 人がボタンを押さなくても動くのか

**証拠**: `WorkflowSchedulerService` が `CronScheduler` を配線し、**30 秒ごとに
ストアと突き合わせて再同期**する(`0ec9c21`)。保存直後に有効になり、cron を
消せば止まる。どちらも以前は再起動するまで反映されなかった。

**評決**: 動く。これが「ワークフロー実行機」と「自動化」の差である。

### 問: 新規ユーザーは実際に使い始められるのか

**証拠**: `loco hash-password` が PBKDF2 ハッシュと、貼り付け可能な
`Auth:Users` ブロックを出力する(パスワードは argv ではなく stdin から読む —
argv はシェル履歴とプロセス一覧に残る)。

**評決**: 使い始められる。

**訂正**: この項目を最初に書いたとき「ハッシュを作る手段が存在せず、誰も
起動できなかった」と断定した。**それは誤りだった。**
`src/Loco.Api/Program.cs` にホスト構築前の argv 検査があり、
`dotnet run --project src/Loco.Api -- hash-password <password>` は実際に動いた
(実行して確認: `PBKDF2$100000$…` を出力した)。
証拠を集める前に結論を書いた例であり、この文書が「問い → 証拠 → 評決」の
順序を強制しているのは、まさにこれを防ぐためである。

真に問題だったのはその経路の**性質**だった: パスワードを argv で受けるため
シェル履歴とプロセス一覧に残り、どの help にも現れないので
`Program.cs` を読まない限り誰も見つけられない。
CLI 版は stdin から読み、`loco help` に載り、貼り付け可能な設定ブロックを
出力する。argv 版は削除した — 同じことをする 2 つ目の経路で、しかも
安全性で劣るものを残す理由は無い。

### 問: エディタは自分の API と通信できるのか

**証拠**: `src/Loco.VisualEditor/src/api/auth.ts` が
`POST /api/v1/authentication/token` でトークンを交換し、`SignInDialog` が
取得まで操作を止める(`3b44f02`)。

**評決**: できる。**ごく最近まで、できなかった** — サインインが存在せず、
設定画面の「API Key」は API が読まないヘッダを、しかも Bearer の**代わりに**
送っていた。入力すると動いていたセッションが 401 になる欄だった。

## 短所(現存)

### 1. 実パッケージに対する `dotnet build` / `dotnet test` が未実行 — 最大

**証拠**: `curl https://api.nuget.org/v3/index.json` は
`CONNECT tunnel failed, response 403`。`/root/.ccr/README.md` はプロキシ 403 を
**組織ポリシーによる拒否**と定義し、迂回を禁じている。

**帰結**: ハーネスの `AddJwtBearer` 配線は自前(トークン検証自体は SDK 同梱の
Microsoft 実装)、Swashbuckle スタブは不活性、実 xunit / FluentAssertions は
このハーネスより賢い。ここで緑でも、実パッケージで緑とは限らない。

**評決**: この環境では解消不能。`docs/ci/ci.yml` の backend ジョブが担う。

### 2. CI 定義が適用できない

**証拠**: GitHub App に `workflows` スコープが無く、`git push` と REST API の
両経路で拒否された(`docs/ci/README.md` に応答を原文で記録)。
現行 `.github/workflows/` の 7 ファイルは 6 つが同じ push で同時に走り、
3 ファイルが**このリポジトリに一度も存在しないパス**を参照している。

**評決**: リポジトリ所有者の操作待ち。手順は `docs/ci/README.md`。

### 3. 実行中のプロセス停止で、進行中の実行が失われる

**証拠**: `JsonFileExecutionStore` は**完了時のみ**書き込む。
`WorkflowSchedulerService` の doc comment が明記するとおり、停止中に逃した
実行は再生されない。

**評決**: 意図的な設計上の限界。再開には最終発火時刻の永続化が要る。

### 4. 条件式が限定文法

**証拠**: エッジ条件は `success` / `error` / `always` と限定的な比較式のみ。

**評決**: 実用範囲だが、任意式ではない。

### 5. lint 警告 55 件

**証拠**: `npm run lint` は 0 エラー / 55 警告。内訳は
`<T extends (...args: any[]) => any>` のようなイディオム的ジェネリック制約か、
型ガードのテストが意図的に `any` を渡す箇所。

**評決**: 意図的。ゲートとしては 0 エラーで機能している。

## 改善案(優先度順)

1. **CI を適用する**(`docs/ci/README.md` の手順)。実パッケージでの初回グリーンが、
   残る全ての「未検証」を消す唯一の手段。
2. **backend ジョブが緑になった時点で**、各コミットの VERIFICATION CAVEAT を外す。
3. 実行の再開(最終発火時刻の永続化)。3 の解消。
4. 条件式の拡張。4 の解消。
